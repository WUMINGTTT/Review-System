## 1. 认证 vs 鉴权 vs 授权

这三个词经常混用，但含义不同：

| 术语 | 英文 | 问题 | 例子 |
|------|------|------|------|
| **认证** | Authentication | 你是谁？ | 用户名 + 密码登录 |
| **鉴权** | Authorization | 你能做什么？ | 管理员能删除用户，普通用户不能 |
| **授权** | Grant | 给你权限 | 管理员把某用户设为评审人 |

**本项目的流程：**
1. **认证**：用户输入用户名密码 → 后端验证 → 签发 Token
2. **鉴权**：每次请求携带 Token → 后端解析出用户身份和角色 → 判断是否有权限

## 2. 密码加密：为什么不能明文存储

### 错误做法：明文存储

```
数据库中: password = "123456"
```

**风险：** 数据库被黑客入侵后，所有用户的密码直接泄露。而且很多用户在多个网站使用相同密码，一处泄露，处处危险。

### 正确做法：哈希加密

```
数据库中: password = "$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy"
```

**哈希的特点：**
- **不可逆**：无法从哈希值反推出原始密码
- **确定性**：相同输入 → 相同输出（用于登录时比对）
- **雪崩效应**：输入改一个字符，输出完全不同

```
"123456"  → "$2a$10$N9qo8uLOickgx2ZMRZoMye..."
"123457"  → "$2a$10$XpH6k8uLOickgx2ZMRZoabc..."
```

### 加盐（Salt）

即使使用哈希，相同密码会产生相同的哈希值。如果两个用户的密码都是 "123456"，数据库中存储的哈希值也相同，黑客可以制作"彩虹表"批量破解。

**加盐的解决方式：** 给每个密码前面加一段随机字符串（盐），再哈希。

```
用户A: hash("123456" + "随机盐A") → "$2a$10$abc..."
用户B: hash("123456" + "随机盐B") → "$2a$10$xyz..."
```

两个用户即使密码相同，存储的哈希值也不同。bcrypt 会自动处理加盐，你不需要手动管理。

## 3. bcryptjs：密码加密工具

### 是什么

bcryptjs 是 Node.js 中最常用的密码哈希库，基于 bcrypt 算法。它是纯 JavaScript 实现（不需要编译原生模块），适合在任何环境中运行。

> 为什么叫 bcryptjs 而不是 bcrypt？
> - `bcrypt`：需要编译 C++ 原生模块，某些系统安装会失败
> - `bcryptjs`：纯 JS 实现，API 完全兼容，推荐使用

### 安装

```bash
pnpm add bcryptjs
pnpm add -D @types/bcryptjs   # TypeScript 类型定义
```

### 核心 API

```typescript
import bcrypt from 'bcryptjs'

// ========== 加密密码 ==========

// hashSync(明文密码, 盐的轮数)
// 盐的轮数越大越安全，但也越慢。10 是推荐值（约 100ms）
const hashedPassword = bcrypt.hashSync('123456', 10)
// 结果: "$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy"

// ========== 比对密码 ==========

// compareSync(用户输入的明文, 数据库中存储的哈希)
// 返回 true 或 false
const isMatch = bcrypt.compareSync('123456', hashedPassword)  // true
const isWrong = bcrypt.compareSync('wrong', hashedPassword)   // false
```

### 在项目中的使用场景

```typescript
// 注册时：加密密码后存入数据库
const hashedPassword = bcrypt.hashSync(req.body.password, 10)
await prisma.user.create({
  data: { username, password: hashedPassword, realName }
})

// 登录时：比对用户输入和数据库中的哈希
const user = await prisma.user.findUnique({ where: { username } })
const isMatch = bcrypt.compareSync(password, user.password)
if (!isMatch) {
  return res.status(401).json({ success: false, message: '密码错误' })
}
```

### 异步版本

```typescript
// hashSync 和 compareSync 是同步的，会阻塞主线程
// 高并发场景推荐使用异步版本
const hashedPassword = await bcrypt.hash('123456', 10)
const isMatch = await bcrypt.compare('123456', hashedPassword)
```

## 4. JWT：JSON Web Token

### 是什么

JWT（JSON Web Token）是一种**身份凭证**。用户登录成功后，服务器签发一个 JWT 给前端，前端在后续请求中携带它，服务器通过验证 JWT 来确认用户身份。

**类比理解：** JWT 就像一张**工牌**。
- 登录 = 打卡上班，前台发给你一张工牌
- 每次进办公室 = 展示工牌给保安看
- 保安不需要打电话问前台"这个人是不是员工"，看工牌就知道了
- 工牌有有效期，过期需要重新打卡

### JWT 的结构

一个 JWT 由三部分组成，用 `.` 分隔：

```
eyJhbGciOiJIUzI1NiJ9.eyJpZCI6MSwibmFtZSI6ImFkbWluIn0.abc123
│      Header（头部）    │        Payload（载荷）          │  Signature（签名）  │
```

| 部分 | 内容 | 说明 |
|------|------|------|
| **Header** | `{"alg": "HS256"}` | 声明使用的签名算法 |
| **Payload** | `{"id": 1, "username": "admin", "roles": ["admin"]}` | 存放用户信息（可被解码查看，不要放密码！） |
| **Signature** | `HMACSHA256(base64(header) + "." + base64(payload), secret)` | 签名，防止篡改 |

### 重要理解

- **Payload 可以被解码**（Base64 解码即可），所以**绝对不能在 Payload 中放密码等敏感信息**
- **签名是防篡改的**：如果有人修改了 Payload 中的内容，签名验证会失败
- **服务器不存储 Token**：JWT 是无状态的，服务器只靠签名验证真伪

### 安装

```bash
pnpm add jsonwebtoken
pnpm add -D @types/jsonwebtoken
```

### 核心 API

```typescript
import jwt from 'jsonwebtoken'

const SECRET = process.env.JWT_SECRET  // 签名密钥，只存在服务器端

// ========== 签发 Token ==========

// sign(载荷, 密钥, 选项)
const token = jwt.sign(
  { id: 1, username: 'admin', roles: ['admin'] },  // 载荷：你想存的信息
  SECRET,                                            // 密钥：用于生成签名
  { expiresIn: '7d' }                               // 选项：7天后过期
)
// 结果: "eyJhbGciOiJIUzI1NiJ9.eyJpZCI6MSw..."

// ========== 验证 Token ==========

// verify(Token字符串, 密钥)
// 成功：返回载荷对象
// 失败：抛出异常（Token 过期或被篡改）
try {
  const payload = jwt.verify(token, SECRET)
  // payload = { id: 1, username: 'admin', roles: ['admin'], iat: 1234567890, exp: 1235172690 }
  console.log(payload)  // 可以取出用户信息
} catch (error) {
  // Token 无效或已过期
  console.log('Token 验证失败')
}
```

### 在项目中的使用场景

```typescript
// 登录成功后签发 Token
const token = jwt.sign(
  { id: user.id, username: user.username, roles: JSON.parse(user.roles) },
  process.env.JWT_SECRET!,
  { expiresIn: process.env.JWT_EXPIRES_IN || '7d' }
)
res.json({ success: true, data: { user, token } })

// 前端收到 Token 后存储到 localStorage
// 后续每次请求在 Header 中携带:
// Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...

// 后端中间件验证 Token
const token = req.headers.authorization?.replace('Bearer ', '')
const payload = jwt.verify(token, process.env.JWT_SECRET!)
req.user = payload  // 把用户信息挂到 req 上，后续控制器可以使用
```

## 5. Zod：请求参数校验

### 为什么需要校验

前端发来的数据**不可信**。可能是：
- 用户忘记填写某个字段
- 用户输入了非法格式（如邮箱没有 @）
- 恶意用户故意发送错误数据攻击系统

**原则：永远不要信任前端传来的数据，后端必须自己校验。**

### 是什么

Zod 是一个 TypeScript 优先的参数校验库。你用链式 API 定义校验规则，Zod 自动校验数据并返回类型安全的结果。

### 安装

```bash
pnpm add zod
```

### 核心 API

```typescript
import { z } from 'zod'

// ========== 定义校验 Schema ==========

// z.object() 定义对象的校验规则
// 每个字段用 z.string()、z.number() 等声明类型
// 登录 Schema（主方式：用户名 + 密码）
const loginSchema = z.object({
  // z.string()：必须是字符串
  // .min(1)：最少1个字符（即不能为空）
  username: z.string().min(1, '用户名不能为空'),

  // .min(1)：密码不能为空
  password: z.string().min(1, '密码不能为空'),
})

// 邮箱登录 Schema（第二方式：邮箱 + 密码，需已绑定邮箱）
const loginByEmailSchema = z.object({
  // Zod v4 中邮箱验证直接用 z.email()，不再挂在 z.string() 后面
  email: z.email('邮箱格式不正确'),
  password: z.string().min(1, '密码不能为空'),
})

// 注册 Schema
const registerSchema = z.object({
  username: z.string().min(3, '用户名至少3个字符'),
  password: z.string().min(6, '密码至少6位'),
  realName: z.string().min(1, '真实姓名不能为空'),

  // z.email().optional()：邮箱为可选项，不填则不验证格式
  // 用户可在注册后通过个人中心绑定邮箱
  email: z.email('邮箱格式不正确').optional(),
})

// ========== 校验数据 ==========

// .parse(数据)：校验成功返回类型安全的数据，失败抛异常
try {
  const data = loginSchema.parse(req.body)
  // data 的类型被自动推断为 { username: string; password: string }
  // 可以安全使用 data.username 和 data.password
} catch (error) {
  // 校验失败，error.errors 包含详细的错误信息
}

// .safeParse(数据)：不抛异常，返回 { success, data, error } 对象
const result = loginSchema.safeParse(req.body)
if (!result.success) {
  // result.error.issues 包含错误详情
  // 每个 issue 有 path（哪个字段出错）和 message（错误描述）
  console.log(result.error.issues)
  // [
  //   { path: ['username'], message: '用户名不能为空', ... },
  //   { path: ['password'], message: '密码至少6位', ... }
  // ]
}
```

### 常用校验规则速查

```typescript
z.string()                    // 字符串
z.string().min(1)             // 非空字符串
z.string().max(100)           // 最多100字符
z.email()                     // 邮箱格式（Zod v4 写法，不再用 z.string().email()）
z.string().regex(/^\d+$/)     // 正则匹配（纯数字）

z.number()                    // 数字
z.number().min(0)             // 最小值0
z.number().max(100)           // 最大值100
z.number().int()              // 必须是整数

z.boolean()                   // 布尔值

z.enum(['a', 'b', 'c'])      // 枚举（只能是这几个值之一）

z.array(z.string())           // 字符串数组
z.array(z.number()).min(1)    // 至少一个元素的数字数组

z.string().optional()         // 可选（可以不传）
z.string().nullable()         // 可以为 null
z.string().default('默认值')   // 不传时使用默认值
```

### 在项目中的使用场景

```typescript
// src/validations/auth.ts
import { z } from 'zod'

// 注册参数校验
export const registerSchema = z.object({
  username: z.string().min(1, '用户名不能为空').max(50),
  password: z.string().min(6, '密码至少6位').max(100),
  realName: z.string().min(1, '真实姓名不能为空'),
  department: z.string().optional(),
  email: z.string().email('邮箱格式不正确').optional(),
  phone: z.string().optional(),
})

// 登录参数校验
export const loginSchema = z.object({
  username: z.string().min(1, '用户名不能为空'),
  password: z.string().min(1, '密码不能为空'),
})

// 在控制器中使用
import { registerSchema } from '../validations/auth'

export const register = async (req, res) => {
  // 校验请求参数
  const parsed = registerSchema.safeParse(req.body)
  if (!parsed.success) {
    return res.status(400).json({
      success: false,
      message: '参数校验失败',
      errors: parsed.error.flatten().fieldErrors,
      // errors: { username: ['用户名不能为空'], password: ['密码至少6位'] }
    })
  }

  // 校验通过，使用 parsed.data（类型安全）
  const { username, password, realName } = parsed.data
  // ... 继续业务逻辑
}
```

## 6. Express 中间件

### 是什么

中间件（Middleware）是 Express 的核心概念。每个请求会依次经过一系列中间件处理，就像流水线上的工人，每人负责一件事。

```
请求 → [中间件1: 解析JSON] → [中间件2: 验证Token] → [中间件3: 路由处理] → 响应
```

### 写法

```typescript
import { Request, Response, NextFunction } from 'express'

// 一个中间件函数接收三个参数
function myMiddleware(req: Request, res: Response, next: NextFunction) {
  // 做一些事情（如验证 Token）

  if (验证通过) {
    req.user = { id: 1 }  // 往 req 上挂数据，后续中间件和路由可以使用
    next()                 // 调用 next() 放行，请求继续流向下一个中间件
  } else {
    res.status(401).json({ message: '未授权' })  // 直接返回错误，不调用 next()
  }
}
```

### 使用方式

```typescript
// 方式1：全局中间件（所有请求都经过）
app.use(myMiddleware)

// 方式2：路由级中间件（只有特定路由经过）
router.get('/users', myMiddleware, userController.list)

// 方式3：多个中间件串联
router.post('/evaluations', authMiddleware, validateMiddleware, controller.create)
```

### 在项目中的认证中间件

```typescript
// src/middlewares/auth.ts

// 认证中间件：验证 JWT Token
export function authMiddleware(req, res, next) {
  // 1. 从请求头取出 Token
  const authHeader = req.headers.authorization
  if (!authHeader || !authHeader.startsWith('Bearer ')) {
    return res.status(401).json({ success: false, message: '未提供认证令牌' })
  }

  const token = authHeader.replace('Bearer ', '')

  // 2. 验证 Token
  try {
    const payload = jwt.verify(token, process.env.JWT_SECRET!)
    req.user = payload  // 把用户信息挂到 req 上
    next()              // 放行
  } catch (error) {
    return res.status(401).json({ success: false, message: '令牌无效或已过期' })
  }
}

// 角色中间件：检查用户是否具有指定角色（必须在 authMiddleware 之后使用）
export function requireRole(...roles: string[]) {
  return (req, res, next) => {
    if (!req.user || !roles.some(r => req.user.roles.includes(r))) {
      return res.status(403).json({ success: false, message: '权限不足' })
    }
    next()
  }
}

// 使用示例：
// router.delete('/users/:id', authMiddleware, requireRole('admin'), controller.delete)
// 含义：先验证 Token → 再检查是否是管理员 → 都通过才执行删除
```

## 7. 完整的认证流程串联

把上面所有技术串起来，看看一次完整的注册和登录请求是怎么工作的：

### 注册流程

```
前端发送 POST /api/auth/register
Body: { "username": "admin", "password": "123456", "realName": "管理员" }
        │
        ▼
┌─ Zod 校验 ──────────────────────────────────┐
│  username: 非空 ✅                            │
│  password: 至少6位 ✅                         │
│  realName: 非空 ✅                            │
│  全部通过 → 继续                              │
└──────────────────────────────────────────────┘
        │
        ▼
┌─ 检查用户名是否已存在 ──────────────────────┐
│  SELECT * FROM users WHERE username = 'admin' │
│  查到 → 返回 400 "用户名已存在"               │
│  没查到 → 继续                                │
└──────────────────────────────────────────────┘
        │
        ▼
┌─ bcrypt 加密密码 ────────────────────────────┐
│  bcrypt.hashSync("123456", 10)                │
│  → "$2a$10$N9qo8uLOickgx2ZMRZoMye..."       │
└──────────────────────────────────────────────┘
        │
        ▼
┌─ 存入数据库 ─────────────────────────────────┐
│  INSERT INTO users (username, password, ...)  │
│  VALUES ('admin', '$2a$10$N9qo8...', ...)    │
└──────────────────────────────────────────────┘
        │
        ▼
    返回 { success: true, message: "注册成功" }
```

### 登录流程

```
前端发送 POST /api/auth/login
Body: { "username": "admin", "password": "123456" }
        │
        ▼
┌─ Zod 校验 ──────────────────────────────────┐
│  username: 非空 ✅  password: 非空 ✅          │
└──────────────────────────────────────────────┘
        │
        ▼
┌─ 查询用户 ───────────────────────────────────┐
│  SELECT * FROM users WHERE username = 'admin' │
│  没找到 → 返回 401 "用户名或密码错误"         │
│  找到 → 继续                                  │
└──────────────────────────────────────────────┘
        │
        ▼
┌─ bcrypt 比对密码 ────────────────────────────┐
│  bcrypt.compareSync("123456", "$2a$10$...")  │
│  false → 返回 401 "用户名或密码错误"          │
│  true → 继续                                  │
└──────────────────────────────────────────────┘
        │
        ▼
┌─ JWT 签发 Token ────────────────────────────┐
│  jwt.sign({ id: 1, roles: ["admin"] }, secret) │
│  → "eyJhbGciOiJIUzI1NiJ9..."                │
└──────────────────────────────────────────────┘
        │
        ▼
    返回 { success: true, data: { user: {...}, token: "eyJ..." } }
```

### 后续请求鉴权流程

```
前端发送 GET /api/users
Header: Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
        │
        ▼
┌─ auth 中间件 ────────────────────────────────┐
│  1. 取出 Token: "eyJhbGciOiJIUzI1NiJ9..."   │
│  2. jwt.verify(token, secret)                 │
│  3. 成功 → req.user = { id:1, roles:["admin"] } │
│  4. next() 放行                               │
└──────────────────────────────────────────────┘
        │
        ▼
┌─ requireRole('admin') 中间件 ────────────────┐
│  req.user.roles 包含 'admin' → next() 放行   │
└──────────────────────────────────────────────┘
        │
        ▼
┌─ 控制器处理 ─────────────────────────────────┐
│  查询数据库，返回用户列表                      │
└──────────────────────────────────────────────┘
```

## 8. 常见问题

### Q: JWT 密钥（JWT_SECRET）可以随便写吗？

可以，但建议是随机的长字符串。密钥的作用是签名，如果太简单（如 "123"），别人可以猜测并伪造 Token。

生成方式：
```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

### Q: Token 存在哪里？

**前端：** localStorage（简单）或 httpOnly Cookie（更安全，防 XSS）。
本项目使用 localStorage。

**后端：** 不存储！JWT 是无状态的，服务器只验证签名，不记录哪个 Token 是有效的。

### Q: Token 过期怎么办？

Token 有效期到了后，`jwt.verify()` 会抛出 `TokenExpiredError`。前端收到 401 响应后，跳转到登录页让用户重新登录。

更高级的做法是使用 **双 Token 机制**：
- Access Token：有效期短（15分钟），用于请求认证
- Refresh Token：有效期长（7天），用于刷新 Access Token

本项目暂不实现双 Token，只用一个 7天有效的 Token。

### Q: bcrypt 的盐轮数是什么？

盐轮数决定加密的计算量。轮数越大越安全，但也越慢。

| 轮数 | 大约耗时 | 适用场景 |
|------|---------|---------|
| 8 | 25ms | 对性能要求极高的场景 |
| 10 | 100ms | **推荐值**，安全与性能的平衡 |
| 12 | 400ms | 高安全要求 |
| 14 | 1600ms | 过慢，不推荐 |

### Q: 为什么登录失败时返回"用户名或密码错误"而不是"用户名不存在"或"密码错误"？

安全考虑。如果分开提示：
- 黑客可以先遍历用户名，找出哪些用户名存在
- 再针对存在的用户名暴力破解密码

合并提示后，黑客无法判断用户名是否存在。

### Q: 401 和 403 有什么区别？

| 状态码 | 含义 | 场景 |
|--------|------|------|
| 401 Unauthorized | 未认证 | 没登录、Token 过期、Token 无效 |
| 403 Forbidden | 已认证但权限不足 | 普通用户访问管理员接口 |
